# Сервис обработки платежей

Сервис принимает платежи через HTTP API, обрабатывает их асинхронно и отправляет
результат на webhook. Платёж и задача на его обработку сохраняются вместе,
поэтому принятый запрос не теряется, если брокер сообщений временно недоступен.

## Как работает обработка

1. Клиент отправляет платёж в API. Сервис сохраняет его со статусом `pending`
   и создаёт задачу на обработку в PostgreSQL в одной транзакции.
2. Фоновый процесс публикует задачу в RabbitMQ.
3. Consumer получает задачу и имитирует работу платёжного шлюза. Результат —
   `succeeded` или `failed` — сохраняется в PostgreSQL.
4. Сервис отправляет результат на указанный `webhook_url`. Ответ `2xx` считается
   успешной доставкой.
5. Если webhook временно недоступен, выполняются повторы. После исчерпания
   попыток событие попадает в очередь `payments.dlq`, а статус webhook становится
   `failed`.

Эмулятор шлюза по умолчанию обрабатывает платёж за 2–5 секунд и выбирает статус
случайно: вероятность успеха задаёт `PAYMENT_SUCCESS_RATE` (по умолчанию `0.9`).
Это вероятность для каждого платежа, а не гарантия определённого количества
успешных или неуспешных платежей в небольшой группе.

Для одного ключа идемпотентности повторный запрос с теми же данными вернёт тот
же платёж. Если данные отличаются, API ответит `409 Conflict`. Платёжные статусы
и статус доставки webhook — отдельные вещи: неудачный webhook не меняет результат
платёжной обработки.

## Технологии

- Python 3.13 и `uv` для управления зависимостями;
- FastAPI и Uvicorn для HTTP API;
- PostgreSQL, SQLAlchemy Async и Alembic для хранения данных и миграций;
- RabbitMQ и FastStream для асинхронной обработки;
- HTTPX для отправки webhook.

## Запуск

Нужны Docker и Docker Compose. Из корня проекта выполните:

```bash
docker compose up --build
```

Compose запускает PostgreSQL, RabbitMQ, миграции базы данных, API и consumer.
API доступно на <http://localhost:8000>, документация Swagger — на
<http://localhost:8000/docs>, интерфейс RabbitMQ — на <http://localhost:15672>.
Учётные данные RabbitMQ по умолчанию: `payments` / `rabbit-local-demo`.

Остановить сервисы, сохранив данные:

```bash
docker compose down
```

Данные PostgreSQL и RabbitMQ хранятся в Docker volumes и сохраняются после
остановки. Чтобы удалить данные, используйте `docker compose down -v`.

## API

Обе ручки требуют заголовок `X-API-Key`. Локальный ключ по умолчанию:
`demo-api-key`.

Создать платёж:

```bash
curl -i http://localhost:8000/api/v1/payments \
  -H 'X-API-Key: demo-api-key-change-me' \
  -H 'Idempotency-Key: order-42' \
  -H 'Content-Type: application/json' \
  -d '{"amount":"100.00","currency":"RUB","description":"Заказ 42","metadata":{"order_id":42},"webhook_url":"https://your-service.example/webhooks/payments"}'
```

При успешном приёме API вернёт `202 Accepted` и идентификатор платежа. Указанный
webhook должен быть доступен из контейнера consumer, принимать JSON и отвечать
кодом `2xx`.

Получить состояние платежа:

```bash
curl http://localhost:8000/api/v1/payments/<payment_id> \
  -H 'X-API-Key: demo-api-key-change-me'
```

Ответ содержит сумму, валюту, описание, metadata, платёжный статус, время
обработки и статус webhook. Возможные платёжные статусы: `pending`, `succeeded`,
`failed`. Для webhook используются `pending`, `delivered`, `failed`.

## Настройки

Compose содержит значения по умолчанию, поэтому для обычного запуска файл `.env`
не обязателен. Чтобы переопределить настройки, создайте `.env` в корне проекта
и укажите в нём нужные переменные.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `API_KEY` | `demo-api-key-change-me` | Ключ доступа к API |
| `PAYMENT_SUCCESS_RATE` | `0.9` | Вероятность успешного ответа эмулятора, от `0` до `1` |
| `PAYMENT_PROCESSING_MIN_DELAY` | `2` | Минимальная задержка эмуляции, секунды |
| `PAYMENT_PROCESSING_MAX_DELAY` | `5` | Максимальная задержка эмуляции, секунды; не меньше минимальной |
| `MESSAGE_MAX_ATTEMPTS` | `3` | Максимальное число попыток обработки, от `1` до `3` |
| `RETRY_BASE_DELAY` | `1` | Начальная задержка перед повтором, секунды |
| `RETRY_MULTIPLIER` | `2` | Множитель задержки повторов |
| `WEBHOOK_TIMEOUT` | `10` | Таймаут запроса к webhook, секунды |
| `OUTBOX_POLL_INTERVAL` | `1` | Интервал проверки очереди outbox, секунды |
| `OUTBOX_BATCH_SIZE` | `100` | Число событий в одном цикле публикации, от `1` до `1000` |
| `BROKER_TIMEOUT` | `5` | Таймаут подключения и подтверждения публикации, секунды |
| `DATABASE_URL` | Формируется Compose | Адрес PostgreSQL; можно задать напрямую при запуске вне Compose |
| `RABBITMQ_URL` | Формируется Compose | Адрес RabbitMQ; можно задать напрямую при запуске вне Compose |
| `POSTGRES_USER` | `payments` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | `payments-local-demo` | Пароль PostgreSQL |
| `POSTGRES_DB` | `payments` | Имя базы данных |
| `RABBITMQ_DEFAULT_USER` | `payments` | Пользователь RabbitMQ |
| `RABBITMQ_DEFAULT_PASS` | `rabbit-local-demo` | Пароль RabbitMQ |

В Compose адреса PostgreSQL и RabbitMQ формируются из имён сервисов и учётных
данных, указанных выше. Для запуска приложения вне Compose задайте `DATABASE_URL`
и `RABBITMQ_URL` напрямую.

Демонстрационные пароли предназначены только для локального запуска. Перед
развёртыванием в другой среде задайте собственные секреты. Изменение учётных
данных PostgreSQL или RabbitMQ не меняет уже созданные учётные записи в
сохранённых volumes.

## Тесты и проверки

В проекте есть тесты API, идемпотентности, сохранения платежа и outbox,
публикации и повторной доставки сообщений, обработки webhook, а также сквозные
сценарии работы consumer. Интеграционные тесты проверяют работу с PostgreSQL и
RabbitMQ, поэтому для полного набора нужен запущенный Docker.

Установить зависимости и запустить тесты:

```bash
uv sync --frozen
uv run pytest
```

Дополнительные проверки:

```bash
uv run ruff check src tests
uv run ruff format --check src tests
docker compose config --quiet
docker build --check .
```

## Логи

В логах API есть HTTP-метод, путь, код ответа, длительность запроса и
`request_id`; он также возвращается в заголовке `X-Request-ID`. Логи consumer
содержат идентификаторы платежа и события, номер попытки и тип ошибки. Секреты,
полное тело запроса и URL webhook не записываются.

## Примечание

Архитектура обработки транзакций упрощена ради скорости реализации, а функционал приложения 
ограничен написанным в ТЗ. Такие технологии как redis для хранения кэша и возможной быстрой 
проверки ключей идемпотентности, а так же helm конфигурация проекта не внедрены.
